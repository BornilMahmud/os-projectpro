Linux Hardware Intelligence.
Inside the Terminal.

SMD-TUI 2.0 is a proposed evolution of the existing SMD-TUI Linux hardware monitor. We will preserve its lightweight Bash foundation and core monitoring capabilities, then improve its structure, usability, configurability, insight and reliability.

What is this proposal about?

We are upgrading an existing open-source terminal utility—not starting a completely new application.

🎯

Our main objective

Turn a useful, mostly read-only hardware dashboard into a more capable, keyboard-driven system monitoring tool while keeping it fast, terminal-native and approachable.

🧭

Our approach

First understand and stabilize the current code. Then refactor it into clear modules, add interactive navigation, build richer monitoring features and verify everything with repeatable tests.

Important distinction: the features marked “Existing” are documented in the current project. Features marked “Proposed” are our planned improvements and should not be presented as already implemented.

02 · What the existing project already does

The original SMD-TUI is a real-time Linux system monitoring dashboard written in Bash. Its current interface is intentionally non-interactive.

Open the original GitHub repository ↗

EXISTING

CPU monitoring

Shows CPU utilization, clock frequency, load average and processor core count.

EXISTING

Memory monitoring

Displays RAM and swap usage, memory pressure information (PSI) and swappiness.

EXISTING

Process overview

Highlights top processes by CPU and memory usage (top entries in the current dashboard).

EXISTING

Thermal and fan data

Reads available temperature sensors, including CPU/NVMe readings, and fan RPM when exposed by the system.

EXISTING

Storage and I/O

Shows root/external drive capacity and disk I/O information; external drives are detected dynamically.

EXISTING

Network monitoring

Displays IPv4 information and upload/download speed.

EXISTING

Battery information

Displays charge, power, estimated remaining time and health when supported hardware data is available.

EXISTING

System identity

Shows machine manufacturer/model, BIOS, kernel, OS, desktop environment, hostname and uptime details.

Other existing behavior: the layout adapts to terminal width, uses compact one- or two-column arrangements, warns when terminal height is insufficient and offers command-line options such as --help, --version, --accent-color and --no-drives.

04 · Our SMD-TUI 2.0 vision

A clean, fast and interactive terminal control center for understanding Linux hardware performance.

⌨️

Keyboard-first experience

Navigate pages, change settings and inspect system information without leaving the terminal.

📊

More useful insight

Show per-core metrics, short-term history, trends and threshold-based warnings—not only current readings.

🧩

Maintainable codebase

Keep collectors, calculations, configuration, user interface and tests separated.

🛡️

Reliable on real machines

Handle missing sensors, unavailable commands, counter resets, small terminals and different Linux environments gracefully.

07 · Proposed modular architecture

We keep Bash as the primary language, but organize the code so each responsibility can be maintained and tested independently.

app.shEntry point, CLI arguments, startup and main loop.
ui/Screen rendering, layout, keyboard input and navigation.
collectors/CPU, memory, sensors, storage and network data collection.
core/Metric calculations, history buffers and alert evaluation.
config/Defaults, external configuration loading and validation.
tests/Unit-style tests, fixtures, smoke tests and integration tests.
Linux sources
/proc · /sys · tools→Collectors→Core processing→UI renderer→Terminal

How the modules work together

  1. Startup: check Bash version, required commands, terminal capabilities and configuration.
  2. Collection: collectors read operating-system counters and available hardware sensor data.
  3. Processing: core functions calculate deltas, rates, percentages, history and alert states.
  4. Rendering: the UI displays the latest data in the selected page and adapts to terminal size.
  5. Interaction: keyboard input changes pages, pauses refresh, updates settings or exits safely.
The exact module filenames and data contracts will be finalized after the Phase 1 code audit. We should refactor incrementally rather than rewrite everything at once.

08 · Example runtime workflow

A predictable collection cycle keeps the interface responsive and prevents one unavailable sensor from breaking the entire dashboard.

Start application→Validate environment→Load config→Collect metrics
Calculate rates→Update history→Evaluate alerts→Render page
Wait for refresh / key→Repeat or exit

Data sources and fallback behavior

InformationLikely sourceFallback behavior
CPU and memoryLinux /proc interfacesShow unavailable/error state if parsing fails.
Hardware temperatures/sys/class/thermal, hwmon and supported sensor toolsShow only detected sensors; never invent a reading.
StorageFilesystem utilities, /proc/diskstats and supported toolsShow capacity separately from optional health data.
Network/proc/net/dev and interface metadataHandle interface disappearance and counter reset.
BatteryAvailable power-supply sysfs entries or supported toolsHide or mark unavailable on desktop systems without a battery.

09 · Implementation roadmap

A phased plan reduces risk and lets us verify each layer before moving forward.

Phase 1 · Audit & stabilize

Understand and protect the existing project

Review the full codebase, document current behavior, establish a baseline, verify dependencies, audit counters and terminal cleanup, and fix confirmed defects.

Phase 2 · Refactor foundation

Build the modular structure

Separate collectors, core calculations, configuration and rendering. Define consistent outputs and add fixture-based tests without removing existing metrics.

Phase 3 · Interactive TUI

Introduce navigation and settings

Add keyboard input, page navigation, help, pause/refresh controls, terminal resize support and external configuration.

Phase 4 · Intelligence features

Add deeper monitoring

Implement per-core details, history graphs, interface selection, alert thresholds, richer storage/thermal views and optional export.

Phase 5 · Quality & release

Validate, document and package

Run regression and compatibility tests, improve installation instructions, update documentation and prepare a versioned release.

10 · Testing and quality strategy

A monitoring tool must be trustworthy. Incorrect metrics can be worse than missing metrics.

Unit-style tests

Test CPU percentage, memory calculations, disk/network deltas, unit formatting and threshold evaluation with known inputs.

Fixture tests

Use controlled sample files that imitate relevant /proc, /sys and sensor outputs, including malformed and missing data.

Integration tests

Verify collectors feed valid data into core calculations and the renderer without requiring every optional sensor.

Terminal tests

Check narrow terminals, resizing, colors, keyboard controls, clean exit and interrupted execution.

Compatibility tests

Validate Bash 4+ behavior and test on selected Linux distributions and different hardware configurations.

Regression tests

Confirm all important original metrics remain available and retain sensible values after each refactor.

11 · Risks and how we handle them

RiskMitigation
Hardware exposes different sensors on different machines.Capability detection, optional collectors and explicit unavailable states.
Linux distributions package tools differently.Startup dependency checks and distro-aware installation documentation.
Refactoring changes existing metric behavior.Capture baseline outputs and maintain regression tests throughout the migration.
Sampling too frequently increases overhead.Configurable refresh interval, efficient reads and bounded history buffers.
Counter resets or interfaces disappearing produce incorrect rates.Validate deltas, detect resets and reinitialize baselines safely.
Terminal is resized or app is interrupted.Handle resize and termination signals; restore cursor and terminal state on exit.
Optional GPU/drive health tools are unavailable.Make advanced readings optional and clearly identify the source/capability.

14 · Scope boundaries and technical decisions

What we are building

  • A Linux terminal application.
  • A Bash-first codebase.
  • Local system monitoring.
  • Interactive keyboard-driven TUI.
  • Optional local tools and native Linux data sources.

What is not in this proposal

  • No web application or browser dashboard.
  • No desktop GUI or graphical control panel.
  • No mandatory cloud backend or account system.
  • No remote monitoring service as a core dependency.
  • No claim that unsupported hardware data can always be read.
Technology principle: keep the application lightweight and Linux-native. Optional utilities may extend hardware visibility, but the core tool should explain missing capabilities clearly rather than fail silently.

Repository and licensing approach

We propose forking the original repository, preserving its history and MIT license notices, then working on a dedicated development branch. Before redistribution, retain the original license and copyright notices and review any added dependency licenses.

15 · Immediate next steps

  1. Fork the original repository and create a dev branch.
  2. Run the current application and existing test script to record a baseline.
  3. Audit the main Bash script and map every existing metric to its data source.
  4. Agree on the initial keyboard controls, page layout and configuration format.
  5. Refactor one collector at a time, adding tests before expanding functionality.
  6. Build the interactive shell only after the data collection foundation is stable.
Recommended first milestone: a stable modular foundation that reproduces the current dashboard's metrics. Once that baseline is proven, we can add navigation and advanced features without losing existing functionality.

০৭ · প্রস্তাবিত Software Architecture

Bash-ই থাকবে মূল programming language। তবে প্রতিটি কাজ আলাদা module-এ ভাগ করব, যাতে code maintain ও test করা সহজ হয়।

app.shApplication চালু করা, CLI argument, startup ও main loop।
ui/Screen design, layout, keyboard input ও page navigation।
collectors/CPU, memory, sensor, storage ও network data সংগ্রহ।
core/Calculation, history buffer ও alert evaluation।
config/Default setting, config load ও validation।
tests/Unit-style test, sample fixture, smoke ও integration test।
Linux data source
/proc · /sys · tools→Collectors→Core processing→UI→Terminal

Module-গুলো কীভাবে কাজ করবে?

  1. Startup: Bash version, প্রয়োজনীয় command, terminal capability ও configuration পরীক্ষা করবে।
  2. Collection: Collector-গুলো Linux-এর system counter ও hardware sensor থেকে তথ্য নেবে।
  3. Processing: Core module percentage, rate, history এবং alert status হিসাব করবে।
  4. Rendering: UI module নির্বাচিত page-এ তথ্য দেখাবে এবং terminal size অনুযায়ী layout বদলাবে।
  5. Interaction: Keyboard input দিয়ে page বদলানো, refresh pause, settings পরিবর্তন বা exit করা যাবে।
Phase 1-এর সম্পূর্ণ code audit-এর পর module-এর exact file name ও data format চূড়ান্ত হবে। একবারে সব code rewrite না করে ধাপে ধাপে refactor করব।

০৮ · Software চালু হলে কীভাবে কাজ করবে?

প্রতিটি refresh cycle-এ data সংগ্রহ, হিসাব, alert যাচাই ও screen update হবে। কোনো sensor না থাকলেও পুরো application বন্ধ হয়ে যাবে না।

Application চালু→System পরীক্ষা→Config load→Data সংগ্রহ
Calculation→History update→Alert check→Screen update
Refresh / Keyboard input-এর অপেক্ষা→আবার চলবে অথবা Exit

কোথা থেকে তথ্য সংগ্রহ করব?

তথ্যসম্ভাব্য Linux Sourceতথ্য না পেলে
CPU ও RAM/procUnavailable বা error state দেখাবে।
Temperature/sys/class/thermal, hwmon ও sensor toolsশুধু পাওয়া sensor দেখাবে।
StorageFilesystem tools, /proc/diskstatsCapacity ও optional health আলাদা দেখাবে।
Network/proc/net/dev ও interface metadataInterface হারালে বা counter reset হলে তা সামলাবে।
BatteryPower-supply sysfs অথবা সমর্থিত toolBattery না থাকলে unavailable দেখাবে।

১০ · Testing ও Quality Assurance

Hardware monitor-এর ক্ষেত্রে ভুল তথ্য দেখানোর চেয়ে তথ্য পাওয়া যাচ্ছে না—এটি পরিষ্কারভাবে দেখানো ভালো।

Unit-style Test

CPU percentage, RAM calculation, disk/network delta, unit formatting ও threshold হিসাব পরীক্ষা।

Fixture Test

আসল hardware ছাড়াই sample /proc, /sys ও sensor output দিয়ে test; missing ও ভুল data-ও পরীক্ষা।

Integration Test

Collector থেকে Core হয়ে UI পর্যন্ত data ঠিকভাবে যাচ্ছে কি না পরীক্ষা।

Terminal Test

ছোট terminal, resize, color, keyboard control, clean exit ও interrupt পরীক্ষা।

Compatibility Test

Bash 4+ এবং নির্বাচিত Linux distribution ও ভিন্ন hardware-এ পরীক্ষা।

Regression Test

নতুন update-এর পরও আগের গুরুত্বপূর্ণ monitoring feature ও হিসাব ঠিক আছে কি না পরীক্ষা।

১৪ · প্রজেক্টের সীমা ও Technology Decision

আমরা যা তৈরি করছি

  • Linux terminal application।
  • Bash-first codebase।
  • Local system monitoring।
  • Keyboard-controlled interactive TUI।
  • Linux-এর native data source ও optional local tool।

এই প্রজেক্টে যা থাকছে না

  • Web application বা browser dashboard নয়।
  • Desktop GUI বা graphical control panel নয়।
  • Cloud backend বা account বাধ্যতামূলক নয়।
  • Remote monitoring service core dependency নয়।
  • যে hardware data দেয় না, তা জোর করে দেখানো হবে না।
Technology Principle: প্রজেক্ট হালকা ও Linux-native রাখব। Optional utility থাকলে অতিরিক্ত তথ্য পাওয়া যাবে; না থাকলে কোন সুবিধা অনুপস্থিত তা পরিষ্কারভাবে দেখাবে।
